# 아키텍처

## 개요
하네스 기반 단계적 구현을 지원하는 프레임워크-agnostic 템플릿 아키텍처. 단순함을 우선으로 하며, 필요 시 확장한다.

## 아키텍처 모드

프로젝트 요구사항에 따라 아래 중 하나를 선택하고, **사용자에게 아래 포맷으로 제안**한 후 승인받는다. (CLAUDE.md §0-1 참조)

| 모드 | 적합한 경우 | 개발기간 | 확장성 | 운영비용 |
|------|------------|----------|--------|----------|
| **풀스택** | 프론트+백엔드 동시 필요 | 4-8주 | 높음 | 높음 |
| **프론트엔드 전용** | BaaS 활용, 별도 백엔드 불필요 | 1-3주 | 보통 | 낮음 |
| **백엔드 전용** | API 서버만 필요, 프론트 별도 | 2-4주 | 높음 | 보통 |
| **서버리스** | 이벤트 기반, 저트래픽, 비용 최적화 | 1-2주 | 보통 | 매우낮음 |
| **Lean Mode** | PoC, MVP, 1-2주 내 배포, 1인 개발 | 3-7일 | 낮음 | 매우낮음 |

> **Lean Mode**: 요구사항이 단순할 때 아키텍처를 과하게 만들지 마라. 파일 10개로 시작해서 필요하면 분리하는 게 원칙이다.

## 옵션 A: 풀스택 (프론트엔드 + 백엔드)

### 프론트엔드 디렉토리
```
src/
├── app/                    # 페이지 라우팅 (Next.js App Router 등)
├── components/             # 재사용 UI 컴포넌트
│   ├── ui/                 # 기본 UI primitives (button, input, modal)
│   └── layout/             # 레이아웃 컴포넌트 (header, sidebar, footer)
├── features/               # 도메인별 기능 모듈
├── hooks/                  # 커스텀 훅 (상태 관리, 데이터 페칭)
├── services/               # API 클라이언트, HTTP 통신
├── stores/                 # 전역 상태 (Zustand, Redux, Jotai 등)
├── styles/                 # 전역 스타일, 테마
├── utils/                  # 공통 유틸리티 함수
├── types/                  # 타입 정의 (공통 interface, type)
└── lib/                    # 서드파티 라이브러리 래퍼
```

### 백엔드 디렉토리
```
src/
├── main.{ext}              # 엔트리 포인트
├── config/                 # 환경 설정 (DB, 캐시, 외부 API)
├── routes/                 # API 라우트 정의
├── controllers/            # 요청 핸들러 (검증, 응답 포맷)
├── services/               # 비즈니스 로직 (순수 함수 우선)
├── models/                 # 데이터 모델, ORM 엔티티
├── middleware/             # 인증, 로깅, 에러 핸들링, CORS
├── utils/                  # 공통 유틸리티
├── types/                  # 타입 정의, DTO
└── tests/                  # 테스트 (단위, 통합)
```

### 핵심 패턴
**요청-응답 파이프라인**:
```
클라이언트 → Controller (검증) → Service (비즈니스 로직) → Model (DB) → 응답
```
- Controller는 요청 검증과 응답 포맷만 담당
- Service는 순수 함수에 가까운 비즈니스 로직
- Model은 데이터 접근만 담당

**에러 핸들링**:
- 전역 에러 미들웨어에서 모든 에러 캡처
- HTTP 상태코드 + 에러 코드 + 메시지 반환
- 로깅 + 모니터링 시스템에 보고

### 데이터 흐름
```
클라이언트 (UI 컴포넌트)
  → API 호출 (axios/fetch, React Query 등)
  → 백엔드 라우트 (인증 미들웨어 통과)
  → 컨트롤러 (요DTO 검증)
  → 서비스 레이어 (비즈니스 로직 실행)
  → 모델/ORM (DB 쿼리)
  → 서비스 (결과 가공)
  → 컨트롤러 (응답 DTO 포맷)
  → 클라이언트 (UI 업데이트)
```

### Trade-off
| 장점 | 단점 | 언제 분리해야 하는가 |
|------|------|---------------------|
| 프론트+백엔드 통합 개발 | 배포 복잡 (2개 서비스) | 프론트/백엔드 팀이 완전히 분리될 때 |
| 타입 공유 | 초기 설정 비용 | 매우 단순한 프로젝트 (Lean Mode 권장) |
| 단일 레포 — 코드 공유 용이 | 빌드 시간 증가 | 모바일 앱만 필요하고 웹 불필요 시 |

## 옵션 B: 프론트엔드 전용 (BaaS)

Supabase, Firebase, Appwrite 등 BaaS를 활용한 프론트엔드 중심 구조.

```
src/
├── app/                # 페이지 (App Router 또는 페이지 라우팅)
├── components/         # UI 컴포넌트
├── lib/                # BaaS 클라이언트, 유틸리티
├── hooks/              # 커스텀 훅 (상태 관리)
├── services/           # BaaS API 래퍼
└── types/              # 타입 정의
```

**데이터 흐름**: `사용자 입력 → Server Action → BaaS → UI 업데이트`

**Trade-off**:
| 장점 | 단점 | 언제 풀스택으로 전환해야 하는가 |
|------|------|------|
| 백엔드 서버/운영 불필요 | BaaS 벤더 락인 | 커스텀 비즈니스 로직 필요 시 |
| 개발 속도 빠름 | 복잡한 쿼리 제한 | 다중 테이블 JOIN 필요 시 |
| 인증/DB 실시간 등 기본 제공 | 가격 스케일링 (대용량 시 비쌈) | 월간 활성 사용자 > 10,000 시 |

## 옵션 C: 백엔드 전용 (API 서버)

```
src/
├── main.{ext}              # 엔트리 포인트
├── config/                 # 설정 (DB, 환경변수)
├── routes/                 # API 라우트 정의
├── controllers/            # 요청 핸들러 (검증, 응답)
├── services/               # 비즈니스 로직
├── models/                 # 데이터 모델, ORM 엔티티
├── middleware/             # 인증, 로깅, 에러 핸들링
└── utils/                  # 공통 유틸리티
```

**Trade-off**:
| 장점 | 단점 | 언제 풀스택으로 전환해야 하는가 |
|------|------|------|
| 프론트/백 분리 — 독립 배포 | 프론트 팀/프로젝트 별도 필요 | 소규모 팀에서 풀스택이 효율적일 때 |
| API 재사용성 높음 (웹/모바일/서드파티) | CORS, 인증 토큰 관리 복잡 | 단일 클라이언트만 있을 때 오버스펙 |
| 백엔드 스케일링 독립적 | 운영 인프라 2배 | |

## 옵션 D: 서버리스

```
functions/              # 서버리스 함수 (API 엔드포인트)
├── api/
│   ├── users.{ext}     # /api/users
│   ├── auth.{ext}      # /api/auth
│   └── webhooks.{ext}  # /api/webhooks
├── shared/             # 공통 유틸리티
└── db/                 # 마이그레이션, 시드
```

**배포**: Serverless Framework, SST, AWS SAM 중 선택 — 선택 시 ADR에 기록

**Trade-off**:
| 장점 | 단점 | 언제 컨테이너/전통 방식으로 전환해야 하는가 |
|------|------|------|
| 트래픽 0일 때 비용 0 | Cold Start 지연 (1-5초) | 저지연 API 필요 시 |
| 자동 스케일링 | 실행 시간 제한 (15분) | 장기 실행 작업 필요 시 |
| 서버 관리 불필요 | 벤더 락인 | 멀티 클라우드 필요 시 |

## 옵션 E: Lean Mode (최소 아키텍처)

PoC, MVP, 빠른 프로토타이핑용. **아래 조건 모두 충족 시 사용**:

- [ ] 배포까지 1-2주 이내
- [ ] 개발자 1-2명
- [ ] 동시 사용자 < 1000
- [ ] 복잡한 비즈니스 로직 없음
- [ ] 인증이 필요 없거나 매우 단순

**구조**: 단일 프레임워크, 단일 레포, 파일 10-20개로 시작.

```
src/
├── main.ts              # 엔트리
├── routes/              # API 라우트
├── services/            # 비즈니스 로직
├── db/                  # SQLite 또는 인메모리
└── types/               # 타입
```

**Lean Mode 규칙**:
1. 백엔드가 필요 없으면 만들지 마라 (BaaS, Supabase 활용)
2. 인증이 필요 없으면 만들지 마라
3. 모듈 분리가 필요하면 그 때 분리 (미리 만들지 마라)
4. DB가 필요 없으면 JSON 파일 또는 인메모리
5. 테스트는 핵심 기능만 (1-2개 E2E)

**Lean Mode 프레임워크 예시**:
- **Node.js**: Hono, Elysia
- **Python**: FastAPI, Flask
- **Go**: net/http + chi

**Lean Mode Trade-off**:
| 장점 | 단점 | 언제 전환해야 하는가 |
|------|------|---------------------|
| 3-7일 내 배포 | 동시 사용자 < 1000 | 트래픽 증가 시 |
| 운영 인프라 불필요 | 복잡한 비즈니스 로직 어려움 | 인증/결제 필요 시 |
| 기술 부채 최소 | 팀 스케일링 어려움 | 개발자 3명 이상 시 |

**필요 시 확장**: Lean → 풀스택/백엔드 전환은 ADR에 기록하고 단계별로 진행.

## 인프라

### 아키텍처 다이어그램

요구사항에 따라 아래 중 적합한 패턴 선택:

**풀스택**:
```
Client → CDN/Edge → 프레임워크 (SSR/CSR) → API Route → DB
```

**백엔드 분리**:
```
Client → CDN/Edge → API 서버 (REST/GraphQL) → 서비스 레이어 → DB
                                    ↳ 외부 API
```

**서버리스**:
```
Client → API Gateway → Lambda/Functions → DB
              ↳ CloudWatch (로깅/모니터링)
```

## 환경변수
`.env.example` 파일 참조.

## 보안
- 모든 API 엔드포인트는 인증 필요
- CORS whitelist 설정
- Rate limiting 적용

## 모니터링
- 에러 트래킹 (Sentry, etc)
- 성능 모니터링 (APM)
- 로그 수집 (ELK, CloudWatch)

## CI/CD
- **CI**: GitHub Actions 등 — 린트, 테스트, 빌드 자동화
- **CD**: Vercel, GitHub Actions, AWS CodeDeploy 등 — 자동/수동 배포
- **배포 트리거**: `main` 푸시 시 자동 배포, 또는 태그 기반 수동 배포
- **환경별 분기**: `main` → Production, PR/preview 브랜치 → Staging, feature 브랜치 → Preview

## 백업 및 복구
- **DB 백업**: 일일 자동 백업, 포인트인타임 리커버리
- **복구 목표**: RTO {목표 시간}, RPO {목표 시간}
- **재해 복구**: 리전 간 복제, 수동 페일오버 절차
