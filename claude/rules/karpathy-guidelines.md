# Karpathy 코딩 가이드라인

LLM 코딩에서 흔한 실수를 줄이기 위한 행동 가이드라인. Andrej Karpathy의 관찰에서 도출됨. 속도보다 신중함을 우선시한다 — 단순 작업은 판단에 맡긴다.

## 1. 코드 전에 생각하라

**가정하지 마라. 혼란을 숨기지 마라. 트레이드오프를 드러내라.**

구현 전에:
- 가정을 명시적으로 밝혀라. 불확실하면 물어라.
- 여러 해석이 가능하면 모두 제시하라 —勝手に 선택하지 마라.
- 더 단순한 접근이 있으면 말하라. 필요한 경우 이의를 제기하라.
- unclear한 부분이 있으면 멈춰라. 뭐가 혼란스러운지 이름 붙여라. 물어라.

## 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 그 이상도 그 이하도 아니다.**

- 요청 외 기능 금지
- 한 번 쓰는 코드에 추상화 금지
- 요청하지 않은 "유연성"이나 "설정 가능성" 금지
- 일어날 수 없는 시나리오에 에러 핸들링 금지
- 200줄로 짰는데 50줄로 가능하면 다시 써라

스스로 물어라: "시니어 엔지니어가 보고 과하다고 할까?" 만약 그렇다면 단순화해라.

## 3. 수술적 변경

**필요한 것만 건드려라. 네가 만든 엉망만 정리해라.**

기존 코드를 수정할 때:
- 옆 코드를 "개선"하지 마라 — 주석, 포맷팅 포함
- 고장 나지 않은 것을 리팩토링하지 마라
- 기존 스타일을 맞춰라 — 네가 다르게 하더라도
- 관련 없는 dead code를 발견하면 말해라 — 지우지 마라

네 변경으로 생긴 dead code는 네가 정리해라:
- 네 변경으로 unused가 된 import/변수/함수를 제거해라
- 기존에 있던 dead code는 요청 없으면 건드리지 마라

테스트: 모든 변경 행은 사용자의 요청과 직접 연결되어야 한다.

## 4. 목표 주도 실행

**성공 기준을 정의해라. 검증될 때까지 반복해라.**

작업을 검증 가능한 목표로 바꿔라:
- "벨리데이션 추가" → "잘못된 입력 테스트를 먼저 작성하고 통과시켜라"
- "버그 수정" → "재현 테스트를 먼저 작성하고 통과시켜라"
- "X 리팩토링" → "변경 전후에 테스트가 통과하는지 확인해라"

멀티스텝 작업이라면 간단한 플랜을 밝혀라:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

명확한 성공 기준이 있어야 독립적으로 반복할 수 있다. 애매한 기준 ("돌아가게 해줘")은 매번 확인이 필요하다.
