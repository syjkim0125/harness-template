# 테스트 규칙

## 커버리지 목표

| 레벨 | 최소 커버리지 | 범위 |
|------|-------------|------|
| 단위 테스트 | 80%+ | 개별 함수, 유틸리티, 컴포넌트 |
| 통합 테스트 | 70%+ | API, DB, 서비스 연동 |
| E2E 테스트 | 핵심 경로 | 사용자 여정, 인증/결제 플로우 |

**커리지는 최소 기준일 뿐이다.** 높은 커버리지 ≠ 좋은 테스트. 동작의 질에 집중해라.

## TDD (테스트 주도 개발)

새 기능과 버그 수정에 **필수**:

```
RED     → 테스트 먼저 작성, 실패 확인
GREEN   → 최소한의 구현으로 통과
REFACTOR → 코드 정리, 테스트 여전히 통과
```

### TDD 필수
- 새 기능 개발
- 버그 수정 (재현 테스트 먼저)
- 리팩토링 (기준 테스트 먼저 작성)

### TDD 생략 가능
- PoC / 스파이크 코드
- 사소한 변경 (단일 행 설정, 문서)

## 테스트 구조 (Arrange-Act-Assert)

```
describe('UserService', () => {
  describe('createUser', () => {
    it('유효한 입력으로 사용자를 생성해야 한다', () => {
      // Arrange: 데이터와 모킹 설정
      const input = { name: 'John', email: 'john@test.com' }
      mockDb.save.mockResolvedValue({ id: 1, ...input })

      // Act: 테스트 대상 함수 호출
      const result = await userService.createUser(input)

      // Assert: 결과 검증
      expect(result).toEqual({ id: 1, ...input })
      expect(mockDb.save).toHaveBeenCalledWith(input)
    })
  })
})
```

## 에지 케이스 — 함수마다 테스트

- [ ] **null/undefined** 입력
- [ ] **빈** 배열, 문자열, 객체
- [ ] **잘못된 타입** (숫자 기대에 문자열)
- [ ] **경계값** (최소/최대, 0, -1)
- [ ] **에러 조건** (네트워크 실패, 타임아웃, DB 다운)
- [ ] **동시 접근** (더블 서브밋, 동시 수정)
- [ ] **대용량 입력** (10K+ 항목)

## 테스트 분류

### 단위 테스트
- **하나의 함수**를 고립시켜 테스트
- 외부 의존성은 모킹 (DB, API, 파일)
- 빠름 (테스트당 < 100ms)

### 통합 테스트
- **컴포넌트 간 상호작용** 테스트 (서비스 + DB)
- 실제/테스트 DB 사용 (모킹 아님)
- 정상 경로 + 에러 경로 둘 다 테스트

### E2E 테스트
- **완전한 사용자 플로우** (로그인 → 탐색 → 구매)
- 스테이징과 비슷한 환경에서 실행
- 핵심 경로만 (모든 에지 케이스 아님)
- 절대 flaky하면 안 됨

## 모킹 전략

### 모킹 대상
- 외부 API (결제, 이메일)
- DB 호출 (통합 테스트는 in-memory DB)
- 파일 시스템
- 시간/랜덤 (`Date.now`, `Math.random`)

### 모킹 금지
- 테스트 대상 시스템
- 도메인 로직 / 순수 함수
- 유틸리티 함수

### 규칙
- 테스트 간 모킹 초기화 (`beforeEach`/`afterEach`)
- 구현체가 아닌 인터페이스로 모킹
- 복잡한 객체는 모킹 팩토리 사용

## Flaky 테스트 방지

**Flaky 테스트는 테스트 스위트를 믿을 수 없게 만든다.** 적극적으로 제거해라.

| 원인 | 해결 |
|------|------|
| 비동기 타이밍 | 명시적 await, waitFor, fake timers |
| 공유 상태 | `beforeEach`/`afterEach`에서 초기화 |
| 테스트 순서 의존 | 순서에 의존하지 않게 작성 |

### Flaky 발견 시
1. 즉시 `skip` 또는 `todo` 처리
2. 24시간 내 원인 조사
3. 수정 후 재활성화
4. 못 고치면 테스트 삭제하고 이유 기록

## CI/CD 통합

```
린트/타입체크 → 단위 테스트 → 통합 테스트 → E2E → 커버리지 리포트
```

### 권장 목표
- 전체 단위 테스트: < 30초 (권장, 프로젝트 규모에 따라 조정)
- 통합 테스트: < 2분 (권장)
- E2E: < 5분 (권장)
- 실패한 테스트는 병합 차단

## 품질 체크리스트

- [ ] 테스트가 독립적 (공유 상태 없음)
- [ ] 테스트 이름이 동작을 설명
- [ ] 외부 의존성은 모킹
- [ ] 정상/에러 경로 둘 다 테스트
- [ ] Flaky 테스트 없음
- [ ] 어설션이 구체적 (`toBeTruthy` 대신 정확 매칭)

## [CUSTOMIZE] 프로젝트별 테스트

- 테스트 프레임워크: 프로젝트 스택에 맞게 선택 (예: Jest, Vitest, pytest, go test 등)
- 컴포넌트 테스트: 프레임워크별 테스트 라이브러리
- E2E: Playwright, Cypress, 또는 HTTP 테스트 도구
- 설정 및 모킹 패턴
